# Asymmetric Cryptography

Asymmetric encryption uses two separate keys, one for encryption and one for decryption:

- The public key, used for encrypting messages and
- The private key, used for decrypting messages.

In contrast to symmetric encryption, the keypair cannot be chosen freely: the two keys have to be mathematically related, so they are always generated together.

For instance, let there be Person A (Alice) and Person B (Bob). Each of them has a public & private key.
The public key needs to be available for everyone who wants to encrypt messages.
The private key must be kept private, as it can be used to decrypt any messages encrypted with the respective public key.

Alice wants to send an encrypted message to Bob.
Firstly, Alice encrypts the message using Bob's public key, and the result is transmitted to Bob.
Then, Bob uses his private key for decrypting the message.

In practice, asymmetric encryption is not used on the message itself: it is slow and limited to data smaller than the key. Instead, a random symmetric key is generated, the message is encrypted symmetrically with it, and only that key is encrypted asymmetrically. This combination is called hybrid encryption and is what TLS, PGP and similar protocols do.

The provided steps serve as a generic illustration about how to create an RSA keypair:

1. Generate two large random prime numbers (p, q).
   It is important to ensure that those prime numbers are generated using a cryptographic random number generator with sufficient entropy,
   as numbers generated by pseudo-random number generators are predictable, making the resulting keypair unsafe.
1. Calculate N = p * q.
1. Calculate Φ(N) = (p-1) * (q-1).
1. Choose e such that 1 \< e \< Φ(N), gcd(e, Φ(N)) = 1.
1. Calculate d such that e * d ≡ 1 (mod Φ(N)).
1. Public key: (e, N).
1. Private key: (d, N).

## Encryption & Decryption

The plain data is defined as m, whereas the encrypted data is defined as c.
Both m and c are treated as unsigned integer.

- **Encryption:**
  - c = m^e mod N.
- **Decryption:**
  - m = c^d mod N.

These formulas describe "textbook RSA", which is **not** secure on its own: it is deterministic (the same m always gives the same c), it only works for m \< N, and small messages can be attacked directly. Real implementations first apply a padding scheme: OAEP for encryption, PSS for signatures.

### Digital Signatures

Digital signatures are cryptographic techniques used to ensure the authenticity & integrity of digital messages.
Here, you'll find an overview about the most common ways to sign & verify messages.

- RSA

In asymmetric encryption, we used the public key to encrypt the data, whereas the private key was used for decrypting the data.
For digital signatures the roles of the keys are swapped: the signer uses the **private** key to sign, and anyone can use the **public** key to verify.
Only a hash of the data is signed, not the data itself, which keeps the operation fast and independent of the message length.

```text
  Signing (private key, done once by the sender)

    data --[hash]--> digest --[sign with sk]--> signature
                                                   |
    data + signature are transmitted together -----+

  Verification (public key, done by every recipient)

    received data --[hash]--> digest  ---,
                                         +--> [verify with pk]
    received signature ------------------'           |
                                                     v
                                        valid -> data is unchanged
                                                 and comes from the
                                                 owner of sk
                                      invalid -> data or signature
                                                 was tampered with
```

Note that signing is not "encryption with the private key". For textbook RSA the two operations happen to look the same mathematically, which is where that wording comes from, but the schemes actually used (RSA-PSS, ECDSA, Ed25519) have no encryption step at all. ECDSA and Ed25519 cannot encrypt anything.

- HMAC (Hash-based Message Authentication Code)

HMAC is another way of verifying digital messages.
In contrast to RSA, a shared secret is used instead of a private key. The message is combined with that secret and hashed, creating a so-called tag.
After transmission, the receiver re-computes the tag from the message and the shared secret and compares it against the received tag. A mismatch means the message was altered in transit, whether by accident or by an attacker.
While HMAC can be used to verify the integrity and authenticity of data, it is important to note that it's not a signing method, and not to be used as such: because both sides know the same secret, either of them could have produced the tag, so an HMAC proves nothing to a third party. A signature does, which is the property called non-repudiation.

### Public Key Infrastructure (PKI)

PKI, also known as Public Key Infrastructure, is a hierarchical system for issuing, distributing and verifying digital certificates.
A certificate is a statement, signed by a certificate authority, that a given public key belongs to a given entity. This solves the problem asymmetric cryptography leaves open: a public key on its own says nothing about who owns it.
A Public Key Infrastructure consists of multiple components:

- Registration Authority:
  - The registration authority is responsible for verifying certificate signing requests & forwarding them to the certificate authority.
  - When you want to get a digital certificate, you need to submit a certificate signing request (CSR) here. As the registration authority needs to verify the user's identity, you need to provide personal information such as
    - Personal information
    - Proof of identity
    - Information about the company to issue the certificate to
- Certificate Authority:
  - The certificate authority is responsible for issuing the digital certificates.
  - After the registration authority validated the user's identity, the certificate authority will create the certificate to be issued to the user.
- Validation Authority:
  - The validation authority is responsible for publishing the current status of issued certificates, so that a certificate can be withdrawn before it expires (for example because the private key was leaked).
  - This status is distributed either as a certificate revocation list (CRL) or queried per certificate via OCSP (Online Certificate Status Protocol). In the case of a code signing certificate, Windows checks the certificate chain and then this revocation status before trusting the signature.

Let's make an example:
You are a software developer, and want to create a computer game.
After you are finished with coding, you want to publish your program, allowing everyone to download it.
Once a user downloads & executes the program, the operating system attempts to verify the publisher by looking for a digital signature within the executable.
That's where PKI comes in: in order to verify yourself as publisher of the program, you need to request a code-signing certificate.
In case it's not present, Windows states that the program was released by an unknown publisher, and therefore cannot be trusted.

Obtaining a code-signing certificate can be quite expensive, especially when it comes to signing kernel-mode drivers.

HTTPS-certificates are also managed via PKI, which are used for providing traffic encryption & verifying the ownership of websites.
Fortunately, HTTPS-certificates are easy & free to obtain. One example of a free certificate authority offering free certificates would be <https://letsencrypt.org>.
